# 图像呈现预言机（ImageOracle）——项目题定稿

- **性质**：不参赛项目题（自选命题，自主发布）
- **产出仓库**：`10-27-imageoracle`（GitHub 公开仓库）
- **署名**：yuluo554
- **版本**：v1（2026-10-27 定稿）
- **形态**：纯本地 CLI。**只读字节**：不解码像素、不做颜色变换、不联网、不写回源文件（报告与派生样本另存）。

## 定位宣言

ExifTool 的官方 FAQ 明确写着 **"ExifTool is not designed as an image validator"**，并把用户推给 JHOVE；ImageMagick 会做，但**会做错**——自家文档承认 `-auto-orient` 存在双重旋转风险；sharp 会自动转，却**留下 XMP 的 `tiff:Orientation`**（[lovell/sharp#4585](https://github.com/lovell/sharp/issues/4585)）；exiftran 是唯一把方向做对的，但**只覆盖 JPEG**，且它是"修"不是"预言"。

本工具做的是**"呈现预言"**：这张图在 Chrome / Safari / Firefox / macOS Preview / Windows 照片 / ImageMagick / libvips / sharp / exiftran 各自会显示成什么样、会不会被转两次、颜色会不会变、动画帧时长会不会被理解错——在**打开它之前**给出可复核的判决与依据，而不是在某个软件里"看一眼感觉不对"。

一句话：**不是校验器，是呈现结果的预言机**。

## 与字体题的品牌隔离切割

本系列已有一题做**字体子集审计**，其对象是**字形层**：sfnt 表结构、`cmap`/`glyf`/`hmtx` 解析、glyph 计数与子集覆盖率。

本题对象是**像素/元数据/色彩层**：Orientation 语义、ICC 字节、容器 chunk 顺序、动画帧时序。两题在**解析器（字节容器 vs 字体表）、规范依据（EXIF/TIFF、ICC、PNG-3、APNG、RFC 9649、GIF89a vs OpenType）、样本渠道（相机/截图/编码器导出 vs 字体文件/网页抓取）**上完全不重叠。本文档不提名任何其他项目。

## 2. 介绍

### 2.1 问题：同一个 Orientation 值，在不同容器/不同软件里结果不同

需求侧最硬的一条证据是 HN 107pts（2025-11-21）**「EXIF orientation info in PNGs isn't used for image-orientation: from-image」**（[46004364](https://news.ycombinator.com/item?id=46004364)，指向 Bugzilla 1627423）：**同一个 Orientation 值，在 JPEG 里被浏览器应用、在 PNG 的 `eXIf` chunk 里却被忽略**。评论 @Linkd（[46005116](https://news.ycombinator.com/item?id=46005116)）：

> "EXIF orientation has always been a massive pain to deal with. Specially with HEIC that keeps getting updated libheifs and causing all sorts of compatibility issues."

色彩侧的另一条（HN 70pts，2025-12-27[^note-date]，[46403048](https://news.ycombinator.com/item?id=46403048) 指向 lr0.org 那篇）：同一张 PNG 在 Chrome 与 Safari/桌面软件里观感不同，朋友说 *"he told me that the image looks foggy"*；作者试遍无效——*"Now it's worse!"* / *"Still foggy. Nothing changed."*；最后靠 `pngcheck -v` 暴露 **`chunk iCCP at offset 0x00025, length 5147`**；`identify` 报的 `Gamma: 0.454545` 被作者点名为 **"ImageMagick's assumption, not file metadata"**；而 `pngcrush -ow -rem gAMA -rem cHRM -rem iCCP -rem sRGB` **无效** → 结论是**只能转 profile 不能 strip**。

[^note-date]: 该条 HN 的日期按代理检索命中的条目元数据记录为 2025-12-27；正文引用以原帖链接为准。若与页面显示不一致，以页面为准（见 data/README 未取项清单）。

这一类"打开之前无法预判"的故障，正是本题的立足点。

### 2.3 规范事实层级（✅ 已核实，逐条入 data/README 台账）

完整台账见 `data/README.md`，此处给题面要用的骨架：

- **EXIF/TIFF 字段 274（0x0112），int16u**。ExifTool 官方标签原文 1–8：1 "Horizontal (normal)"、2 "Mirror horizontal"、3 "Rotate 180"、4 "Mirror vertical"、5 "Mirror horizontal and rotate 270 CW"、6 **"Rotate 90 CW"**、7 "Mirror horizontal and rotate 90 CW"、8 **"Rotate 270 CW"**。**特别确认：6 是顺时针 90°，不是逆时针**（这是最容易搞反的一点，已核实）。来源：<https://exiftool.org/TagNames/EXIF.html>
- **ICC profile 头 128 字节**，ExifTool 给出的字段偏移：`ProfileCMMType@4`、`ProfileVersion@8`、`ProfileClass@12`、`ColorSpaceData@16`、`ProfileConnectionSpace@20`、`ProfileDateTime@24`、`ProfileFileSignature@36`（`acsp`）、`PrimaryPlatform@40`、`CMMFlags@44`、`DeviceManufacturer@48`、`DeviceModel@52`、`DeviceAttributes@56`、`RenderingIntent@64`、`ConnectionSpaceIlluminant@68`、`ProfileCreator@80`、`ProfileID@84`（其后 100–127 保留）。**字段名按 ExifTool 原文**：是 "CMMFlags" 不是 "ProfileFlags"；是 "DeviceManufacturer/DeviceModel"。
- `ProfileClass` 取值 `mntr`(display)/`scnr`(input)/`prtr`(output)；`RenderingIntent` 0 Perceptual / 1 media-relative colorimetric / 2 saturation / 3 ICC-absolute colorimetric。
- **PNG 3rd ed（W3C）Table 7**：「The IHDR chunk shall be the first chunk」；IEND「Shall be last」；PLTE「Before first IDAT」（color type 0/4 不得出现 PLTE）；「Multiple IDAT chunks shall be consecutive」；tRNS「After PLTE; before IDAT」（color type 4/6 不得出现）；`acTL/eXIf/pHYs/sPLT`=Before IDAT；`cHRM/cICP/gAMA/iCCP/sBIT/sRGB`=Before PLTE and IDAT；`bKGD/hIST/tRNS`=After PLTE; before IDAT；**`fcTL`=One may occur before IDAT; all others shall be after IDAT**；`fdAT`=After IDAT。
- **CRC 原文**：「A four-byte CRC calculated on the preceding bytes in the chunk, including the chunk type field and chunk data fields」（**不含 length**）；「The CRC is always present, even for chunks containing no data.」
- **iCCP 与 sRGB 互斥（PNG-3 原文）**：「If the iCCP chunk is present, the sRGB chunk should not be present」
- **APNG（Mozilla spec）**：`acTL`「must appear in the stream before any IDAT chunks」，字段 `num_frames`(u32)/`num_plays`(u32,0=无限)；`num_frames`「must equal the number of fcTL chunks」，不一致「should be treated as an error」；`fcTL` 字段 `sequence_number/width/height/x_offset/y_offset/delay_num/delay_den/dispose_op/blend_op`；「The first fcTL chunk must contain sequence number 0」；「sequence numbers ... must be in order, with no gaps or duplicates」；「Decoders must treat out-of-order APNG chunks as an error」；`delay_den` 为 0 时「treated as if it were 100」。
- **WebP（RFC 9649）**：`ANIM` = Background Color(u32，字节序「[Blue, Green, Red, Alpha]」) + Loop Count(u16,0=无限)；`ANMF` 字段「Frame Duration | 24 (uint24) | The time to wait before displaying the next frame, in 1-millisecond units.」
- **GIF89a**：Disposal Method 0「No disposal specified」、1「Do not dispose」、2「Restore to background color」、3「Restore to previous」、4–7「To be defined」；Delay Time 单位 **1/100 秒**。

**由上面可判定的单位不一致事实**：GIF 与 APNG 默认都是 **1/100 s**（APNG 由 `delay_num/delay_den` 决定，常见退化即 1/100），WebP 是 **1 ms**，AVIF 帧时长不在图像样本内、而在 ISOBMFF track 时序里。→ **跨格式转帧时的量级错误（10× / 1×）可以被静态检出**，这是 M4 的验收核心。

## 3. 任务要求（首期 5 模块）

**全局确定性纪律（M1–M5 共用）**
- 输入只读：打开文件以只读方式，绝不写回源文件；输出报告写到 `out/` 或 stdout。
- 逐字节可复现：同一输入在同一构建下输出字节相同（排序稳定、JSON key 有序、浮点不出现——统计量一律用整数/定点）。
- 所有判决项带 `evidence`：`{"spec": <规范条款 ID>, "quote": <原文片段>, "location": {"container":"png","chunk":"iCCP","offset":37}}`。
- 退出码一处定义（见 `data/README.md`「数值口径纪律」）：0 = 无风险项；1 = 有 warning；2 = 有 error/不可判；3 = 输入不可解析（此码不参与"判决"）。
- 不猜：像素内容不可读时（不解码像素是硬约束），所有涉及"像素实际如何"的结论只能落到 `gray` / `unknown`，并在报告里显式标 `confidence:"gray"`。

### M1 `orientation` 判定器

**输入**：单文件（JPEG / TIFF / PNG(`eXIf`) / WebP(`EXIF`) 首期支持；见范围限定）。可选 `--emit-fixtures` 走样本生成。

**读什么**
- JPEG：APP1 `Exif\0\0` → TIFF 头 → IFD0 的 tag 274；IFD1（缩略图）的 tag 274；APP1 XMP（`http://ns.adobe.com/xap/1.0/\0`）中的 `tiff:Orientation`。
- TIFF：IFD0 / IFD1 的 tag 274。
- PNG：`eXIf` chunk 内 TIFF 结构（注意：PNG 的 `eXIf` 不含 `Exif\0\0` 前缀，首期按 chunk 数据直接按 TIFF 解析，见 data/README 的边界注记）。
- WebP：`EXIF` chunk 内（可能含 `Exif\0\0` 前缀，做前缀探测）。

**输出**
1. 每个来源的原始值（`exif.ifd0.orientation=6`、`exif.ifd1.orientation=1`、`xmp.tiff:Orientation=6`）；
2. **应施加的变换**（用变换矩阵表达，见 `data/README.md`「8 元变换矩阵」）：对值 1–8 分别给出 `{flip_h, flip_v, rotate_cw_deg}`；
3. **有效宽高**：5/6/7/8 交换 W/H（值 2/3/4 不交换）；
4. 值域越界（0/9+/非 int16u）→ `error: orientation_out_of_range`。

**验收（硬性）**
- 造 8 个样本（`exiftool -Orientation#=N` 生成，N=1..8），每个样本的 `orientation`、变换矩阵、有效宽高与 ExifTool 官方语义**逐项对应**。
- **单测断言：`orientation=6` 的变换必须是顺时针 90°**；`orientation=8` 必须是顺时针 270°（等价逆时针 90°）。断言文案直接引用 ExifTool 标签原文，避免日后被"改反"。
- 镜像族（2/4/5/7）必须同时给出 `flip` 与 `rotate`，不得只给旋转。

**确定性纪律**：不推导"应该显示成什么样"以外的任何像素事实；不因 `eXIf` 缺失就默认 1（缺失 → `absent`，与"值等于 1"分列）。

### M2 双重旋转探测器

**输入**：M1 的解析结果的超集（同文件可同时出 M1+M2 报告）。

**判决条件（三条件取或，命中即报，报出命中了几条）**
1. `IFD1.orientation ≠ IFD0.orientation`（缩略图与主图方向不一致）；
2. XMP `tiff:Orientation` 与 EXIF tag 274 冲突（值不同，或一方存在一方缺失且另一方非 1）；
3. 声明方向与像素内容不符的**启发式**：利用容器自带宽高（JPEG SOF/PNG IHDR/WebP VP8X、TIFF tag 256/257）与"大边位置"启发式做**弱判决**——只能给 `suspicion`，并显式标 `confidence:"gray-heuristic"`，不得输出"确定转错"。

- "谁在什么时候会转两次"：给出**软件 × 触发链**的最小集合，例如：
  - `sharp.autoOrient()`：EXIF 已归 1 但 XMP `tiff:Orientation` 仍在 → 下游读 XMP 的软件会再转一次（对应 #4585）；
  - `jpegtran -copy all -rotate 90`：主图转了，IFD1 缩略图 "copied as-is and not transformed" → 缩略图与主图不一致；
  - `ImageMagick -auto-orient`：源图已被错误修正但 tag 未重置 → 文档原文承认 "may be rotated wrongly a second time"。
- 每条结论必须带 `evidence`（指向工具文档原文或规范条款）。

**验收（硬性）**
- 复现 **sharp #4585**：用 sharp `autoOrient()` 处理带 XMP `tiff:Orientation` 的样本，M2 必须命中条件 2，并指出"EXIF 已为 1、XMP 仍为 N"。
- 复现 **jpegtran -copy all**：`jpegtran -rotate 90 -copy all` 后 M2 必须命中条件 1（IFD1 未同步）。
- 两类样本每次生成后**先跑 M1 确认基线**，再跑 M2，避免把"生成器 bug"当成"探测器通过"。

**确定性纪律**：条件 3 只出 `suspicion`；不得把启发式命中和条件 1/2 的确定性命中混在同一得分里（分列 `certain` / `heuristic`）。

### M3 `color` 体检器

**输入**：同 M1 的容器集合 + JPEG CMYK（APP14 Adobe）样本。

**检查项**
1. **ICC 存在性**：JPEG APP2 `ICC_PROFILE\0`（含多段拼接、段号 `i/n` 连续性）、PNG `iCCP`、WebP `ICCP`、TIFF tag 34675。
2. **128B 头字段合法性**（按 `data/README.md` 的偏移表逐字段）：
   - `ProfileFileSignature@36 == "acsp"`；
   - `size`（头前 4 字节，BE u32）与载体长度一致（JPEG 多段需拼接后比对；PNG `iCCP` 解压后比对——**首期不做 zlib 解压**，见下方边界）；
   - `ProfileClass@12 ∈ {mntr, scnr, prtr}`（其余值报 warning，如 `spac`、`abst`、`nmcl` 属 ICC 合法但非本工具首期白名单，标 `info`）；
   - `ColorSpaceData@16`、`ProfileConnectionSpace@20` 是否在已知集合内（`RGB `、`CMYK`、`GRAY`、`XYZ `、`Lab `）；
   - `RenderingIntent@64 ∈ 0..3`。
3. **PNG `iCCP` ↔ `sRGB` 互斥**：两者同时存在 → `warning: iccp_srgb_conflict`（引 PNG-3 原文）。
4. **`gAMA` / `cHRM` 有无**：单独存在、与 `iCCP`/`sRGB` 并存的组合分别标注（这是 lr0 案例的成因面）。
5. **CMYK JPEG（APP14）警告**：存在 Adobe APP14 `transform` 字段时标 `warning: cmyk_jpeg`，并引 @amiantos 的"浏览器渲染不一致"原话作为需求依据（不是技术依据）。
6. **位深**：JPEG SOF 精确度、PNG IHDR bit depth、WebP bitstream 位深（能在不解码像素的前提下读到才报，读不到标 `unknown`）。
7. **无标记时的默认假设表**（这是本模块的"观念交付物"，必须逐条配出处）：
   | 情形 | 本工具记录的"各方默认" | 出处 |
   |---|---|---|
   | PNG 无任何色彩 chunk | 多数软件假设 sRGB | @kloch 31112951、@meindnoch 50137766（✅ 原话） |
   | 有 `sRGB` chunk | 显式 sRGB | PNG-3 |
   | 有 `gAMA`/`cHRM` 无 `iCCP` | 依实现解释，常见"仅取 gamma" | lr0 案例（`Gamma: 0.454545` 被点名为 ImageMagick 假设）✅ |
   | 有 `iCCP` | 应用该 profile（但 Chrome/Safari 行为分歧，单来源，标⬜） | lr0 案例 ✅ 单来源 |
   | ICC 缺失且调 libvips `icc_import` | **不假设 sRGB**：按"embedded → input_profile 文件 → 内置兼容 profile"三处搜索 | libvips 文档原文 ✅ |
   | JPEG 无 ICC | 常见假设 sRGB（非规范强制） | ⬜ 待补原文 |

**验收（硬性）**
- 复现 lr0 案例的**元数据形态**（不是像素观感）：构造一张带 `iCCP` 的 PNG，M3 必须报出 `iCCP present (len=N)`、`sRGB absent`、`gAMA/cHRM` 有无，并在消费者矩阵里给 Chrome=应用 / Safari=不应用 的**分歧标注**（并标该结论为单来源⬜）。
- 损坏 profile 三类各命中：**截断**（长度 < 128 或 < 声明 size）、**size 字段错**（声明 2000、实到 1500）、**`acsp` 坏**（改成 `acsq`）。
- 默认假设表在报告里逐行出现，每行带 `source` 字段。

**确定性纪律**：不做颜色变换、不引入 lcms；"看起来会不会变"只出 `risk: high/medium/low/unknown` + 依据，绝不出具体色值。PNG `iCCP` 压缩流首期不解压（标 `unknown: compressed_profile_not_inspected`）——这是有意的范围限定，不是遗漏。

### M4 `container` 校验器

**输入**：PNG/APNG、WebP（含动图）、GIF、JPEG。

**检查项**
1. **PNG chunk 顺序（严格按 PNG-3 Table 7）**：IHDR 首、IEND 末、PLTE 位于首个 IDAT 前且 color type 0/4 不得出现、tRNS 位于 PLTE 后 IDAT 前且 color type 4/6 不得出现、`cHRM/cICP/gAMA/iCCP/sBIT/sRGB` 位于 PLTE 与 IDAT 前、`bKGD/hIST/tRNS` 位于 PLTE 后 IDAT 前、`acTL/eXIf/pHYs/sPLT` 位于 IDAT 前、`fcTL` 允许一个在 IDAT 前其余在 IDAT 后、`fdAT` 在 IDAT 后。
2. **CRC**：按原文"chunk type + chunk data"（**不含 length**）计算并比对；每个 chunk 都应存在 CRC（含空数据 chunk）。`--fix` 语义学 oxipng 的反面：我们**不修**，只报。
3. **IDAT 连续性**：`Multiple IDAT chunks shall be consecutive`。
4. **APNG**：`num_frames == fcTL count`；首 `fcTL` 序号为 0；序号单调无缺口无重复；`delay_den==0` 按 100 处理；`acTL` 在首个 IDAT 前。
5. **WebP**：`ANIM`（BGRA 字节序、Loop Count u16=0 无限）、`ANMF` Frame Duration 24-bit **ms**；`ANMF` 内部数据边界。
6. **GIF**：Disposal Method（含 4–7「To be defined」是否出现）、Delay Time **1/100 s**、GCE 位置与帧序。
7. **JPEG 段顺序与 progressive/baseline**：SOI→APPn→DQT/DHT→SOF0/SOF2→SOS 的基本顺序、多 SOS 与 progressive 的一致性、APP14 位置。
8. **跨格式帧时长单位**：把各格式帧时长**归一化到 ms**（`gif: delay*10`、`apng: delay_num/delay_den*1000`、`webp: 原值`），并给出"若按错误单位解读会差多少倍"的静态判定（10× / 1×）。**AVIF 帧时长在 track 时序里，不在图像样本内 → 首期只报 `not-in-band`**。

**输出**：错误清单（`container/chunk`、`offset`、`spec`、`quote`、`severity`）+ 归一化后的帧时长表。

**验收（硬性）**
- 每类造 **2 例**：PNG 顺序 2 例（如 `gAMA` 放在 IDAT 后、第二个 IDAT 非连续）、CRC 2 例（坏 CRC、缺 CRC）、APNG 2 例（`num_frames` 与实际 `fcTL` 数不符、序号跳号）、WebP 2 例（`ANMF` duration 截断、`ANIM` 循环数位置错）、GIF 2 例（`dispose=4`、delay 单位被按 ms 写入的样本）。
- **跨格式帧时长单位不一致必须被静态检出**：同一段 100 ms 的动画分别写成 GIF(10)、APNG(10/100)、WebP(100)，M4 报告里三者归一化后都等于 100 ms；把 WebP 写成 10 或把 GIF 写成 100 必须报 `unit_mismatch`。

**确定性纪律**：只做结构判定，不渲染、不拼接帧；偏移一律给**绝对文件偏移**；CRC 算法实现必须有已知向量单测。

### M5 `consumers` 渲染矩阵报告

**输入**：M1–M4 的结果。

**输出**
1. **消费者矩阵**（JSON + 人读表）：行 = Chrome / Safari / Firefox / macOS Preview / Windows 照片 / ImageMagick / libvips / sharp / exiftran；列 = `会应用方向?`、`会应用 ICC?`、`会丢哪些 chunk?`、`双重旋转风险`、`动画帧时长解读`、`依据`。
2. **风险清单**：每条 = `{consumer, risk, severity, evidence, confidence}`。
3. **处理前后 diff**：给定一条"加工命令"（如 `oxipng --strip safe`、`sharp.rotate()`），输出"加工后哪些 chunk 会消失 / 哪些字段会变"，例如"过一遍 `oxipng --strip safe` 将丢失 `gAMA`/`cHRM` → 颜色将变"。
   - 依据：oxipng `--strip safe` 保留集原文 = `cICP, iCCP, sRGB, pHYs, acTL, fcTL, fdAT`（**`gAMA`/`cHRM` 不在 safe 保留集**）；`--strip all` 原文 "CAUTION: 'all' will convert APNGs to standard PNGs."；`--fix` 原文 "Do not perform checksum validation of PNG chunks."。
4. **退出码**：按全局纪律。

**验收（硬性）**
- 每行结论**必须挂依据**：`evidence.kind ∈ {spec, tool-doc, hn-quote}`，`tool-doc` 必须给 URL + 原文片段；`confidence` 为 `certain` / `single-source` / `gray`。
- **不得凭印象**：任何没有 `evidence` 的行，CI 直接判失败（自测脚本 `selftest_evidence_complete`）。
- 至少覆盖 4 个"加工命令"的 diff：`oxipng --strip safe`、`oxipng --strip all`、`sharp.rotate()`、`exiftran`（JPEG only）。

**确定性纪律**：矩阵内容来自 `data/README.md` 的工具能力矩阵与规范台账，不来自运行时猜测；工具版本号必须写进报告头（星数/版本是可过期事实）。

## 7. 边界与非目标

| 不做 | 理由 |
|---|---|
| **EXIF/隐私剥离** | 已商品化：`exif remove strip metadata` 检索 40+ 仓、strypt 41★、多个 Show HN；再做没有增量。 |
| **真实颜色变换** | 不引入 lcms/ICC 引擎；避免与 jsColorEngine 42★、iccDEV 187★ 正面竞争；本题只"体检 + 预言"。 |
| **C2PA / 内容溯源** | 属合规审计禁区，且与"呈现"无关。 |
| **色彩校色** | 需硬件（校色仪）与显示器，纯字节无法完成。 |
| **ELA / 篡改取证** | 结论非确定性，HN 已有公开质疑；与"可复核判决"的定位冲突。 |
| **HEIC / AVIF 转码** | 转码不是预言；libheif / libavif（2208★）已占位。AVIF 只做"帧时长不在样本内"的静态说明。 |
| **纯 JPEG 段解析器** | go-jpeg-image-structure 77★ 已占位 → 并入 M4，不单独立项。 |
| **IFD1 一致性单独立项** | 太窄 → 作为 M2 的条件 1。 |
| **PNG `iCCP` 解压后的 profile 内省** | 首期不解压（避免引入 zlib 依赖与"解压后仍不可判"的灰区），标 `unknown: compressed_profile_not_inspected`。 |
| **像素内容判定（解码像素）** | 硬约束：只读字节。所有"像素实际如何"只出 `gray` / `suspicion`。 |

**隐私红线**：纯本地、零网络；真实照片不入仓；样本全部程序化合成（或从合成样本派生）。

**品牌隔离**：不提名、不比较任何其他同系列项目；文档只谈本工具与外部工具。

**首期范围限定**：
- 容器：JPEG、TIFF、PNG/APNG、WebP、GIF。AVIF/HEIC 只做"元数据位置说明"，不做解析。
- 语言：待决（见 00-README 决策记录）。
- 不做 GUI、不做服务端、不做 watch 模式。
